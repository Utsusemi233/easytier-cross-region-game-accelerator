# 部署中遇到的问题与处理方法

这份说明按实际流量经过的顺序排查：客户端、接入网关、分流规则、纠错隧道、出口。登录成功、节点可见和游戏场景可用是不同检查。每次修复后，用新建立的应用连接确认变化。

先按 [OpenWrt 部署文档](DEPLOY.md) 建立并验证两地网关。电脑要复用已有纠错线路，再读 [原生客户端接入已有网关](NATIVE-GATEWAY.md)。下面的地址都是示例，具体日志和测量留在自己的私人记录中。

## 1. 先确定故障在哪一层

| 观察 | 下一项检查 | 修复后需要的证据 |
| --- | --- | --- |
| 客户端没有虚拟地址 | 私有入口是否可达、两端网络凭据是否一致、已有节点是否在线 | 官方 CLI 可见节点，获得未冲突的虚拟地址 |
| 能登录，进入场景失败或仍走旧线路 | 实际场景 UDP、系统路由、网关分类条件 | 新场景连接命中规则，双向流量进入正确隧道 |
| 标记计数增加，家庭请求仍失败 | 策略路由、源地址、家庭允许范围、出口 NAT | 对应连接有双向数据，隧道源 HTTPS 成功 |
| 普通 Wi-Fi 可用，新网络不可用 | DNS 重定向、IPv6、转发区域、MTU 与其他 VPN | 同一设备切换网络后能进入场景，普通网络仍可用 |
| 服务都在运行，时好时坏 | 当前端点签名、验证年龄、实际对端、接口重载 | 新地址验证成功后恢复；失效时切回当地线路 |
| 客户端和游戏网络表现不同 | 两者是否进入同一后端，是否多了一段接入 | 分别核对入接口、分类、源 NAT 和出口 |

按一层一层的顺序处理。先保留可用的原线路和恢复文件，再修改新增入口；不要同时换身份、DNS、IPv6、纠错参数和无线网络，否则难以判断是哪项改动有效。

## 2. 配置保存了，路由没有按预期工作

EasyTier 的命令行选项和 TOML 字段不总是同名。2.6.4 的手工 IPv4 路由字段是根级 `routes`，命令行选项是 `--manual-routes`。在 TOML 中写一个未经确认的 `manual_routes` 字段，不能据此认定客户端装载了路线。核对配置、官方 CLI 和系统路由三者。[配置定义](https://github.com/EasyTier/EasyTier/blob/v2.6.4/easytier/src/common/config.rs)

Windows 遇到多个匹配项，先选最长前缀；前缀长度相同时再比较度量。因此，新增 `0.0.0.0/0` 可能输给原有默认路线。已有网关负责选出口的方案，可以用 `0.0.0.0/1` 与 `128.0.0.0/1` 将 IPv4 交给该网关；网关随后决定家庭或当地出口。[Windows 路由选择](https://learn.microsoft.com/en-us/windows-hardware/customize/desktop/unattend/microsoft-windows-tcpip-interfaces-interface-routes-route-metric)

两段 `/1` 会改变全部 IPv4 的接入路径。启用前确认物理入口和底层隧道有更具体的绕行路线，普通流量在网关仍有可用当地出口。该写法只适合明确采用这一结构的部署，不能作为所有原生直连场景的默认配置。

```powershell
Get-NetRoute -AddressFamily IPv4 |
  Sort-Object DestinationPrefix |
  Select-Object DestinationPrefix, NextHop, InterfaceAlias, RouteMetric
```

## 3. 登录能用，游戏场景没有加速

启动器、账号登录、下载和实时场景可以使用不同服务器及协议。验证一条登录 TCP 或 HTTPS 连接，只说明那条请求可用。应观察游戏真正进入场景后的 UDP 目的地址、端口和来源设备，再查看网关的 conntrack 与规则计数。

如果服务端每次变化，只保留一个服务器 `/32` 会使后续连接漏出。已有部署可复用其区域 IPv4 地址集合或维护好的目标集合，给新的入接口使用相同条件。保留底层入口绕行、DNS/NTP 排除和协议限制。区域分配记录描述的是地址注册地区，不是应用身份；海外 CDN 和 IPv6 仍需单独处理。

电脑原生入口也要匹配来源网段和新 TUN 接口。只在原游戏 Wi-Fi 的 `br-game` 上挂规则，不能覆盖从另一个 EasyTier 接口进入的流量。规则加载后，让应用重新建立连接再观察。

## 4. 分流标记有了，家庭出口却收不到返回包

检查的不止是标记，还包括对应 `ip rule`、策略路由表、WG 接口与源地址。已有 WireGuard 链路可能只允许其原内层来源；新增客户端网段虽然进入 WG，返程仍可能无法成立。

管理员可以选择扩展对端允许范围，或在接入网关上只对“新客户端网段 → 家庭 WG”做源 NAT，使用该链路已允许的内层源地址。需要按已有结构选择，不能把新网段的所有流量都随意伪装到家庭隧道上。当地出口流量继续采用原 WAN 转发/NAT。

```sh
ip -4 rule
ip -4 route show table all
ip -4 addr show dev wg_game
nft list chain inet fw4 mangle_prerouting
nft list chain inet fw4 forward
```

核对实际连接的双向数据、源 NAT 和绑定隧道源的 HTTPS。标记计数增加只表示发生匹配。

## 5. DNS 和 IPv6 把问题带到另一条路径

新增网络可能被原有 DNS 重定向截获，DNS 请求被拒绝时，节点通信仍可能正常。在已有 DNS 链中检查新入接口的处理；需要绕过时，把条件限制在该接口和客户端来源网段。普通 Wi-Fi 和其他插件的 DNS 设置应保留。

IPv4 登录成功而游戏失败，也可能与 IPv6 可用性有关。用原网络与新网络做对照，确认 IPv6 地址、默认路线和 relay 没被误删。关闭 IPv6 会改变对照条件，不应该把它当成所有网络错误的默认修复。

仅维护 IPv4 集合的线路不能声称覆盖所有 IPv6 应用目标。按协议分别验证，记录没有进入家庭路线的流量。

## 6. 隧道把自己的底层连接也送进去了

在完整 IPv4 路由下，ZeroTier 等底层网络可能把新 EasyTier 虚拟网卡或虚拟网段作为物理路径候选。结果可能是递归、频繁换路径或短时掉线。

检查底层程序的接口和物理网段排除配置，加入本项目新增 TUN/网段，合并已有设置。每台设备的底层身份仍保留自己的原文件；共享的是 EasyTier 网络凭据。外出后应重新核对底层承载，不能从局域网直连可用推断酒店或热点可用。

## 7. 防火墙重载后，新增入口的规则消失

直接添加到 nft 的规则通常不能替代持久化配置。网络接口重连、ZeroTier 恢复和 fw4 重载都可能清掉临时规则。

新增入口需要自己的重载回调或 fw4 include。重载时按唯一注释/自有表重新生成规则；服务停用后，回调应依据状态开关停止重建。清理只删除该入口自己的分类、forward、DNS bypass 和 NAT，不撤销原游戏网络的规则。

查看重载命令的返回值及日志，再查看实际规则和语法检查。若命令返回非零，报告具体原因；实际规则恢复与命令成功是分别记录的结果。

## 8. 端点会变，监控要检查当前连接

动态模块只接受配置中的授权对端及近期有效路径。检测到公网 IPv6 或端点变化时，先隔离失效家庭路线，更新实际变化项，再探测隧道和家庭 HTTPS。验证成功才恢复；验证失败或过期时采用当地路线。

默认配置中，轮询为 5 秒，周期探测为 60 秒，验证凭据有效期为 180 秒，地址变化等待为 15 秒。这些是调度和门控参数，不是端到端恢复时间保证。用户自己的配置可以不同。

本版热插拔通知增加了自定义 WAN 名称和 `zt*` 设备匹配。ZeroTier 的 UCI 网络名不必叫 `zerotier`；已匹配事件可唤醒检测，轮询仍作兜底。检查事件是否真的生成唤醒记录，也检查新地址是否通过出口验证。

## 9. 增加接入端以后出现抖动

先分别测“电脑 → 本地网关”和“网关 → 家庭”，查看 socket 掉包、CPU、内存和 UDP 缓冲上限。新的原生入口可以单独启用多线程，并根据内存余量调整缓冲上限；不要因加了入口就重写已有效的家庭骨干。

调整 `rmem_max`/`wmem_max` 上限与提高系统默认缓冲不同。保留原值，每次改一项，并比较同一时间窗的计数增量。服务重启可能重置累计计数，不能用重启后的较小累计数声称掉包改善。短时 RTT 没有尖峰也不代表长期没有抖动。

## 10. 最后验收应用效果，而不只验收连接

两端 FEC 参数必须一致。高冗余会消耗额外流量；`2:30` 的理论总包数为 16 倍，额外 1500%，不是通用最佳设置。同步记录数据包和字节增量、封装成本、服务器、时段和丢包，才能判断是否值得保留。

先检查真实路线和出口，再对同设备、同服务器、同场景做关闭/开启对照。行情、企业应用、TCP 请求和游戏 UDP 各有自己的服务端与传输方式；某个游戏变快不能替代其他软件验收。

把通过、失败、未测试分别写入私人报告。两个无 TUN 实例可以检查 DHCP 分配，不能替代另一台实体电脑的网卡与应用测试。开机恢复、整体公网前缀变化、外出网络和停用清理也分别测试，见 [验收方法](ACCEPTANCE.md)。
